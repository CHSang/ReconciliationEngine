# Copilot Implementation Plan — CSV-Only Financial Reconciliation Demo

## 1. Purpose

Build a command-line Java application that reconciles records from DBS and Quantifeed for three types:

- `POSITION`: compare investment holdings.
- `TRANSACTION`: compare executed trades.
- `CASH`: compare cash balances.

The application reads two CSV files, validates and normalizes their data, matches records, compares the relevant values, and produces one combined `reconciliation-results.csv` file plus a clear console summary. The goal is a working demo whose output is checked against the input data.

## 2. Confirmed decisions and scope

- Java 21, Spring Boot 3.x, Spring Batch, Maven.
- CSV input and output only. **No PostgreSQL, database, JDBC, Flyway, Docker, REST API, or UI.**
- Automated JUnit test suite is not required. Prioritize building, running, inspecting the actual output, checking it against source records, fixing defects, and rerunning.
- Input files: `dbs-records.csv` and `quantifeed-records.csv`.
- Output file: `reconciliation-results.csv`.
- All three reconciliation types match records by `correlationId`.
- Matching is strictly one-to-one: each `correlationId` must identify exactly one record in DBS and exactly one record in Quantifeed for the applicable reconciliation scope.
- `executionId` is independently generated by each source. It is for traceability only and must never be used as the cross-system matching key or required to be equal.
- Normalize both sources into a common canonical model **before matching**.
- Use `BigDecimal` for financial numbers; exact comparison is the default unless a tolerance is explicitly configured.
- Do not silently discard invalid, unmatched, or duplicate records.
- Write output to a temporary file and publish it only after successful processing.

## 3. End-to-end workflow

1. Validate job arguments and input files.
2. Read the original CSV rows and retain source file name, row number, and original values for traceability.
3. Validate each row against the source-specific input format.
4. Normalize DBS and Quantifeed rows into the same canonical model.
5. Check missing and duplicate `correlationId` values within each source and reconciliation type.
6. Match by `correlationId` one-to-one across all three reconciliation types.
7. Compare the normalized business fields for each matched pair.
8. Classify matched records, financial breaks, missing counterparts, and invalid-data issues.
9. Write the combined output CSV and a separate `reconciliation-errors.csv` for rows that cannot safely enter reconciliation, if applicable.
10. Print a run summary and verify record counts and output contents against the input records.

Configure Spring Batch with a supported database-free/resourceless job repository for the selected Spring Batch version. Do not add a database dependency to satisfy Spring Batch metadata.

## 4. Input CSV contract

Both files use this shared header:

`sourceSystem,sourceBatchId,businessDate,reconciliationType,accountId,transactionId,correlationId,executionId,referenceId,securityId,side,quantity,price,amount,currency,balance,settlementDate,sourceCreatedAt`

Files:
- `dbs-records.csv`
- `quantifeed-records.csv`

### Field notes

- `sourceSystem`: expected to identify `DBS` or `QUANTIFEED`; validate against the file being read.
- `sourceBatchId`: source batch identifier.
- `businessDate`: business-calendar date for the reconciliation.
- `reconciliationType`: required; one of `POSITION`, `TRANSACTION`, `CASH`.
- `accountId`: account identifier, subject to the source contract.
- `correlationId`: cross-system matching key for **all three** reconciliation types.
- `executionId`: independently generated source-system identifier for traceability only.
- `transactionId` and `referenceId`: source/business references; do not substitute them for `correlationId` without an explicitly approved mapping rule.
- `securityId`, `side`, `quantity`, `price`, `amount`, `currency`, `balance`, `settlementDate`: values used according to reconciliation type.
- `sourceCreatedAt`: source timestamp; normalize to UTC when it represents an instant and its zone/offset is known.

Fields irrelevant to a type may be blank. Required fields must be defined per type and documented. Do not assume source formats or source time zones without inspecting representative data or receiving an explicit configuration.

## 5. Data normalization

Normalization is a dedicated layer applied after parsing/validation and before matching. Keep original source values and normalized values available for troubleshooting. Normalization must make equivalent representations comparable without hiding real differences.

### 5.1 Currency

- Normalize recognized currency codes to uppercase ISO 4217 codes (for example, `usd` to `USD`).
- Use explicit source-specific mappings for source-specific labels or aliases.
- Do not perform FX conversion as part of normalization.
- Unknown or ambiguous currency values must be reported as data-quality errors, not guessed.

### 5.2 Dates and timestamps

- Parse business dates to ISO `LocalDate` format (`yyyy-MM-dd`) while preserving the business-calendar date; do not shift business dates to UTC.
- Parse timestamps with an explicit offset or a configured source time zone and normalize instants to UTC.
- If a timestamp has no offset and no configured source time zone, report a normalization error rather than guessing.
- Support source-specific date/time formats through configuration.

### 5.3 Numeric values

- Parse quantity, price, amount, and balance as `BigDecimal`, never `double`.
- Configure decimal and thousands separators separately for each source where needed.
- Do not silently round or truncate values.
- Do not treat missing numeric values as zero.
- Apply tolerances only when explicitly configured for a specific field; default tolerance is zero.

### 5.4 Identifiers and controlled values

- Trim surrounding whitespace where safe.
- Normalize `side` aliases to `BUY` or `SELL` only using an explicit mapping (for example, `B` to `BUY` if confirmed by the source contract).
- Normalize case only for fields where case is not meaningful.
- Preserve leading zeros in identifiers.
- Do not alter `correlationId` in a way that could cause different identifiers to collide. Only trim surrounding whitespace if approved as part of the identifier contract.
- Use explicit mappings if security identifiers differ across systems.
- Treat blank, whitespace, and literal `NULL` consistently only where the source contract defines them as null values.

### 5.5 Normalization traceability

For relevant fields, retain enough information to show:
- original DBS value;
- normalized DBS value;
- original Quantifeed value;
- normalized Quantifeed value;
- normalization/mapping rule applied, where useful.

If normalization fails, do not continue with a guessed value. Report the file, row number, field, rejected value, and reason.

## 6. Matching rules — all types use correlationId

**`correlationId` is the universal cross-system matching key for POSITION, TRANSACTION, and CASH.** The relationship is strictly one-to-one. Do not use type-specific fields, `executionId`, `transactionId`, or `referenceId` as fallback matching keys.

Validate correlation ID uniqueness within each source for the relevant reconciliation scope. The scope must at minimum distinguish reconciliation type and business date; include account or batch context if required by the confirmed source contract. Do not silently resolve collisions by choosing a record.

Handling rules:
- One record in DBS and one record in Quantifeed for the same correlation ID and type: compare the pair.
- Only in DBS: output a `BREAK` with `MISSING_IN_QUANTIFEED`.
- Only in Quantifeed: output a `BREAK` with `MISSING_IN_DBS`.
- Missing correlation ID: report a data-quality error/break; do not guess a match.
- Duplicate correlation ID in either source: report a duplicate-ID data-quality break. Do not arbitrarily pair or aggregate records.
- If the same correlation ID appears across different reconciliation types, treat records as separate type-scoped records; do not cross-match types.
- Different `executionId` values are expected and do not prevent a match.

## 7. Reconciliation comparison rules

### POSITION
Match by `correlationId`; compare:
- `securityId`
- `quantity`

A quantity difference produces `QUANTITY_MISMATCH`. A security ID difference produces `SECURITY_MISMATCH`.

### TRANSACTION
Match by `correlationId`; compare:
- `securityId`
- `side`
- `quantity`
- `price`
- `amount`
- `currency`
- `settlementDate`

Use specific break types where possible, such as `SECURITY_MISMATCH`, `SIDE_MISMATCH`, `QUANTITY_MISMATCH`, `PRICE_MISMATCH`, `AMOUNT_MISMATCH`, `CURRENCY_MISMATCH`, and `SETTLEMENT_DATE_MISMATCH`.

### CASH
Match by `correlationId`; compare:
- `currency`
- `balance`

A balance difference produces `CASH_BALANCE_MISMATCH`. A currency difference produces `CURRENCY_MISMATCH`.

### Shared comparison behavior

- Compare normalized values, not raw source representations.
- Calculate numeric difference consistently as `DBS value - Quantifeed value` when both values exist and are comparable.
- If multiple fields differ for one pair, emit one output row and list every difference in `differenceDetails`.
- Choose one deterministic primary `breakType` using a documented priority order.
- Do not aggregate records implicitly.

## 8. Statuses and error handling

### Reconciliation statuses

- `MATCHED`: a valid one-to-one pair exists and all required comparisons agree.
- `BREAK`: a value mismatch, missing counterpart, duplicate identifier, or other reconciliation discrepancy exists.
- `PENDING`: only when an explicit configured business rule says the missing counterpart is still expected. Without such a rule, a missing counterpart is a `BREAK`.

### Invalid input policy

Distinguish input/normalization errors from financial reconciliation breaks.
- Invalid file structure, missing required headers, or unreadable input: stop the run and report the error.
- Invalid individual rows: report file, row number, field, value, and reason in `reconciliation-errors.csv` (or a clearly documented console report). Continue only if the invalid rows can be safely isolated and no records are silently lost.
- Do not classify an invalid or unnormalizable value as `MATCHED`.
- If a run cannot produce a complete, trustworthy output, fail the run and do not publish a partial final output.

## 9. Output CSV contract

Main output file: `reconciliation-results.csv`.

Recommended columns:

`runId,businessDate,reconciliationType,correlationId,accountId,referenceId,securityId,currency,dbsSourceRecordId,quantifeedSourceRecordId,dbsExecutionId,quantifeedExecutionId,dbsSourceRowNumber,quantifeedSourceRowNumber,dbsValue,quantifeedValue,difference,status,breakType,differenceDetails`

Add original/normalized value detail columns or a dedicated detail file if needed to keep the main CSV readable. Do not remove source traceability to make the output shorter.

Rules:
- One output row per matched pair or one-sided source record.
- Never silently drop unmatched records.
- Every row has `reconciliationType`, `correlationId` where present, and `status`.
- `breakType` is blank for `MATCHED` and populated for `BREAK`/`PENDING` as applicable.
- `difference` is blank when not applicable or one side is missing; otherwise use the documented sign convention.
- Preserve both source execution IDs, even when they differ.
- Include all field-level differences in `differenceDetails`.
- Keep column order and date/number formatting stable.
- Invalid rows that cannot safely be reconciled should be visible in the error report, not silently omitted.

Suggested break types include:
- `QUANTITY_MISMATCH`
- `PRICE_MISMATCH`
- `AMOUNT_MISMATCH`
- `BALANCE_MISMATCH` / `CASH_BALANCE_MISMATCH`
- `CURRENCY_MISMATCH`
- `SECURITY_MISMATCH`
- `SIDE_MISMATCH`
- `SETTLEMENT_DATE_MISMATCH`
- `MISSING_IN_DBS`
- `MISSING_IN_QUANTIFEED`
- `MISSING_CORRELATION_ID`
- `DUPLICATE_CORRELATION_ID`
- `TIMING_DIFFERENCE`
- `OTHER_MISMATCH`

## 10. Result traceability and run summary

Every result should be traceable to the exact source row(s). Retain source file name, source row number, source batch ID, source record identifiers, and original/normalized values as appropriate. Avoid using `executionId` as a match key; it is included only to help investigate source records.

Print a console summary calculated from the actual run, for example:

```text
RECONCILIATION SUMMARY
Business date: <actual date>
DBS rows read: <count>
Quantifeed rows read: <count>
Rows normalized: <count>
Rows rejected: <count>

POSITION:    matched <n>, breaks <n>, pending <n>
TRANSACTION: matched <n>, breaks <n>, pending <n>
CASH:        matched <n>, breaks <n>, pending <n>

Output: <actual output path>
Run status: COMPLETED / COMPLETED WITH BREAKS / FAILED
```

These counts must come from the actual run, not hardcoded values. The summary must account for input rows, valid normalized rows, rejected rows, matched pairs, and one-sided records without double-counting.

## 11. Configuration and run experience

Use `application.yml` or command-line arguments for input/output paths and source-specific normalization settings. Example only; configure the real source formats after inspecting representative CSV data:

```yaml
reconciliation:
  input:
    dbs: ./input/dbs-records.csv
    quantifeed: ./input/quantifeed-records.csv
  output:
    file: ./output/reconciliation-results.csv
    error-file: ./output/reconciliation-errors.csv
  normalization:
    dbs-time-zone: UTC
    quantifeed-time-zone: UTC
    trim-text: true
  comparison:
    default-tolerance: 0
```

Do not assume both sources use UTC or the same decimal/date format; configure each source separately when required. Provide simple documented commands to build and run the application. The README must explain input placement, configuration, output paths, statuses, break types, and how to inspect results.

## 12. Safe reruns and output publishing

- Generate a new `runId` per execution.
- Never append to an old result file.
- Write output to a temporary file in the target directory, validate it, then replace the final output after successful processing.
- Preserve the previous completed output if processing or export fails.
- Rerunning the same inputs should produce equivalent business results, apart from run-specific metadata such as `runId`.
- No durable batch history or database-backed restartability is required in this CSV-only demo.

## 15. Manual execution and verification checklist

No automated test suite is required. During actual execution, verify these cases using sample files and inspect the output:

- Exact match for POSITION, TRANSACTION, and CASH.
- Differences in quantity, price, amount, currency, settlement date, and cash balance.
- Same `correlationId` with different `executionId` values still matches.
- Record exists only in DBS or only in Quantifeed.
- Missing or duplicate `correlationId` is clearly reported.
- Equivalent timestamps in different offsets normalize to the same instant.
- Equivalent currency codes and decimal representations normalize consistently.
- Business dates are preserved rather than shifted by time-zone conversion.
- Invalid/ambiguous normalization is reported instead of guessed.
- All original source rows are accounted for in results or error reporting.
- Counts in the console summary agree with the actual output.
- Failed runs do not replace the previous complete output.
- Reruns do not append duplicate output rows.

A successful process exit alone is not proof of correctness. Inspect the generated files and compare them with the source data before declaring the demo complete.
